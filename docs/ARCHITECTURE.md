## 1. Резюме и границы проекта

**[ИСТОЧНИК]** Цель — локальная система производства видео: проекты → сцены → шоты → референсы/озвучка → промпты → рендер → ревью. Linux-ноутбук (16 GB) отвечает за управление, MacBook Pro M3 (18 GB Unified Memory) — за ресурсоёмкие модели.

**[РЕКОМЕНДАЦИЯ]** Главный результат MVP — **один воспроизводимый шот**, который можно поставить в очередь, сгенерировать, просмотреть, повторить с известными параметрами и одобрить. Объединение шотов в ролик — отдельный этап после MVP.

### 1.1. В MVP

- Проект, сцена, шот и привязка изображений.
- Ручной промпт или простой локальный prompt-builder; не блокировать MVP сложным мультиагентным конвейером.
- Проверенный ComfyUI workflow, очередь с одним тяжёлым заданием на Mac.
- Статус, отмена, восстановление после сбоя, сохранение каждой попытки и просмотр результата.
- Минимальный Web UI для управления шотами и очередью.

### 1.2. После MVP

- TTS, тайминг реплик и синхронизация с шотами.
- Character bible, VLM, RAG, consistency-checker.
- Каталог референсов и similarity search.
- Монтаж, звуковая дорожка, субтитры, экспорт целого видео.
- Batch-рендер, дополнительные воркеры, чат-управление.

### 1.3. Не обещать до проверки

- Полную независимость от облака **при финальном качестве**: исходный документ сам допускает облачный финальный рендер.
- Стабильный Wan I2V + IP-Adapter + ControlNet на M3/18 GB.
- Конкретные пиковые RAM, скорость и качество: цифры исходника — гипотезы, а не замеры.
- Реализацию за 18 дней или UI в 500–800 строк без упрощения требований.

### 2.3. Спорные решения

|#|Решение в v1.1|За|Против|Вердикт v1.2|
|---|---|---|---|---|

## 3. Целевая архитектура

### 3.1. Размещение

```text
Browser
   |
   v
Linux (controller, 16 GB)
  Reverse proxy + minimal React UI
          |
          v
  FastAPI Orchestrator ---- PostgreSQL (projects, shots, jobs, attempts)
          |                        |
          |                  Artifact metadata
          v
  Artifact store (диск Linux + HTTP API; NFS/SMB опционально)
          ^
          |
MacBook M3 (factory, 18 GB)
  Worker Agent (pull: claim/heartbeat/upload) -- resource lock -- ComfyUI (127.0.0.1) / Ollama / TTS
                                  (one heavy job at a time)
```

**[РЕКОМЕНДАЦИЯ]** Linux — единственный владелец бизнес-состояния и очереди. Mac Worker Agent — исполнитель с локальным диспетчером ресурсов. Прогресс идёт от Worker Agent к Orchestrator; UI читает его через SSE и периодический GET как fallback. **[v1.2]** Модель взаимодействия — **pull**: Worker Agent сам обращается к Orchestrator по HTTPS (claim, heartbeat, события, загрузка артефактов). Orchestrator никогда не вызывает Mac напрямую, поэтому на Mac нет входящих портов, а сон и перезагрузка Mac выглядят как истёкший lease.

### 3.2. Границы ответственности

|Компонент|Ответственность|Не должен делать|
|---|---|---|
|Orchestrator|API, валидация, jobs, зависимости, учёт версий, аудит|Запускать тяжёлые модели|
|Worker Agent|Принять lease/job, подготовить workflow, запустить/отменить, выгрузить результат|Самостоятельно менять бизнес-статус approved|
|ComfyUI|Исполнение конкретного зафиксированного workflow|Управлять проектами и историей шотов|
|Prompt service|Предложить промпт и структурированные замечания|Перезаписывать утверждённый character bible|
|Keyframe service **[v1.2]**|Получить/сгенерировать стартовый кадр шота (T2I или загруженный референс), сохранить как артефакт|Запускать видео без подтверждённого кадра|
|TTS service|WAV, transcript, word/line timing с указанием точности|Автоматически определять монтаж без подтверждения|
|Storage|Хранить оригиналы и производные артефакты|Быть единственным местом хранения метаданных|

### 3.3. Технологический выбор для MVP

- **FastAPI + SQLAlchemy + Alembic + PostgreSQL**.
- **Очередь на PostgreSQL** с `FOR UPDATE SKIP LOCKED`; Redis не нужен до появления обоснованной нагрузки.
- **Worker Agent на Python** как тонкий адаптер к ComfyUI HTTP/WS API. Стороннюю библиотеку выбирать только после проверки репозитория, версии, лицензии и функционала.
- **React + TypeScript + Vite** с простыми экранами. Сначала список шотов, затем Kanban.
- **Артефакты [v1.2]**: хранить на диске Linux, content-addressed (sha256); Mac скачивает входы в локальный кэш и загружает результаты через HTTP API с проверкой хэша. NFS/SMB — необязательная опция только для чтения.

## 4. Модель данных и жизненный цикл

### 4.1. Сущности

```text
Project 1--N Scene 1--N Shot
Project 1--N Character / ReferenceAsset
Shot    1--N RenderAttempt 1--N Artifact
Job     1--N JobDependency (parent job)
Job     0..1 Scene / 0..1 Shot   (CHECK: ровно одно из двух) [v1.2]
```

**[РЕКОМЕНДАЦИЯ]** Минимальный набор таблиц:

|Таблица|Ключевые поля|
|---|---|
|`projects`|id, title, status, bible_version, created_at, updated_at|
|`scenes`|id, project_id, sequence_no, title, audio_artifact_id|
|`shots`|id, scene_id, sequence_no, target_duration_frames, timeline_fps, current_prompt_revision_id, continuity_from_shot_id, status, approved_attempt_id **[v1.2]**|
|`prompt_revisions`|id, shot_id, prompt, negative_prompt, model_id, created_at|
|`jobs`|id, kind, scene_id, shot_id (CHECK: ровно один), status, priority, payload, attempts, max_attempts, run_after, lease_owner, lease_until, heartbeat_at, external_id (ComfyUI prompt_id), idempotency_key, error_code, created_at, updated_at **[v1.2]**|
|`job_dependencies`|job_id, depends_on_job_id|
|`render_attempts`|id, shot_id, job_id, kind (keyframe/video/postprocess), prompt_revision_id, input_artifact_ids, workflow_version, model_hash, seed, native_fps, parameters, worker_id, duration_s, peak_mem_mb, status, created_at **[v1.2]**|
|`artifacts`|id, attempt_id, kind, storage_key, sha256, bytes, mime_type, created_at|
|`reference_assets`|id, project_id, kind, storage_key, sha256, metadata (`references` — зарезервированное слово SQL)|
|`workers` **[v1.2]**|id, name, last_seen_at, capabilities, comfy_version, status|

`duration_frames` и `fps` предпочтительнее плавающих секунд для точного монтажа; исходные timestamps из TTS можно хранить отдельно в миллисекундах. Для статусов нужны `CHECK`/enum, индексы и уникальность `(scene_id, sequence_no)`. **[v1.2]** Естественная идемпотентность: частичный уникальный индекс «не более одного активного render-job на шот» (см. 13.3); `native_fps` модели и `timeline_fps` проекта хранить раздельно, приводить к одному fps на этапе постобработки.

### 4.2. Статусы

**Job:** `pending → leased → running → completed`; альтернативно `failed`, `cancel_requested → cancelled`, `retry_wait`, `lease_expired` **[v1.2]** (воркер замолчал: задание не перезапускается, пока воркер не вернулся и не сообщил состояние своих `prompt_id`, либо пока не сработал явный таймаут/ручное решение). Истёкший lease приводит к сверке состояния внешней задачи **до** повторного запуска.

**Shot:** `draft → prompt_ready → keyframe_ready → queued → generating → review → approved` **[v1.2]** (`keyframe_ready` — стартовый кадр получен и подтверждён); при отклонении `review → changes_requested → prompt_ready/keyframe_ready/queued`. Job status и Shot status не являются одной и той же сущностью.

**RenderAttempt:** immutable metadata; новый seed, prompt или workflow = новая попытка. Утверждение версии не уничтожает остальные результаты.

### 4.3. Согласованность

- Публиковать файл атомарно: временное имя → проверка размера/hash → rename → запись Artifact.
- Не хранить в БД абсолютные пути конкретной ОС: `projects/<id>/shots/<id>/attempts/<id>/output.mp4`.
- Нельзя удалять исходные медиа при удалении job; очистка — отдельная политика retention.
- `updated_at` обновлять при каждой модификации, вводить миграции Alembic.
- **[v1.2]** Артефакты content-addressed: загрузка с `sha256` в заголовке, повторная загрузка того же хэша — no-op; сервер сам вычисляет и сверяет хэш перед публикацией.
- **[v1.2]** Промежуточные файлы (кадры, латенты) не хранить после завершения попытки; хранить MP4 и, для утверждённых шотов, исходник максимального качества.

## 6. Очередь, ресурсы и отказоустойчивость

### 6.1. Очередь

1. Транзакционно создать Job и зависимости в PostgreSQL.
2. Выбрать готовую задачу через `FOR UPDATE SKIP LOCKED`, назначить lease и владельца.
3. Перед запуском получить эксклюзивный Mac resource lock.
4. Записать внешний ComfyUI `prompt_id` и регулярно обновлять heartbeat.
5. После завершения сверить результат, опубликовать Artifact, атомарно закрыть Job.
6. При потере соединения сначала запросить состояние `prompt_id`; **не запускать дубликат вслепую**.

`priority` влияет только на выбор _ожидающих_ задач; нельзя прерывать уже идущий рендер без явной политики. Задачи TTS/LLM/видео могут иметь разные лимиты retry. Отмена — best effort с подтверждением фактической остановки. **[v1.2]** Cancel для ComfyUI: если `prompt_id` выполняется — `POST /interrupt`; если ждёт в очереди — удалить из очереди; в обоих случаях подтвердить результат по `/history`. Воркер обязан быть единственным клиентом своего ComfyUI, иначе interrupt заденет чужую задачу. Если lease истёк (`lease_expired`), воркер при возвращении вызывает `resume` и сообщает состояние своих `prompt_id` — только после этого job переводится в `retry_wait` или `completed`.

### 6.2. Resource manager Mac

**[РЕКОМЕНДАЦИЯ]** Один диспетчер для всех тяжёлых операций: ComfyUI, Ollama, F5-TTS и Whisper. Перед запуском проверять свободную память, memory pressure, swap и загруженные модели. После выполнения явно освобождать ресурсы через подтверждённые механизмы конкретных сервисов. Пауза 2–3 секунды **не гарантирует** освобождения памяти. **[v1.2]** Конкретные механизмы **[ПРОВЕРИТЬ на используемых версиях]**: у ComfyUI есть эндпоинт `POST /free` (выгрузка моделей и очистка памяти); у Ollama модель выгружается запросом с `keep_alive: 0`; для TTS/Whisper самый надёжный вариант — отдельный процесс на задачу, который завершается после работы. После каждой выгрузки диспетчер сверяет фактическое состояние памяти, а не доверяет ответу сервиса.

### 6.3. Сбои, которые нужно протестировать

- Перезапуск Linux при `running` job.
- Перезапуск Mac во время sampling.
- Разрыв сети/отмонтирование общего хранилища.
- OOM/ошибка модели и повторная постановка.
- Отмена во время рендера и после завершения.
- Два одинаковых запроса `render` подряд.
- Успешный рендер при потере callback/WS-события.
- **[v1.2]** Сон Mac и закрытие крышки во время sampling; отключение питания; термодроссель при серии рендеров.
- **[v1.2]** Два воркера делают `claim` одновременно (гонка) — job достаётся ровно одному.
- **[v1.2]** Обрыв загрузки артефакта на середине; несовпадение `sha256`.
- **[v1.2]** Cancel, когда в ComfyUI выполняется другой prompt.

### 6.4. Mac как рабочая станция [v1.2]

- Запускать Worker Agent через `launchd` с `caffeinate -i` (или эквивалентным assertion), чтобы система не засыпала во время задания; ноутбук подключён к питанию.
- Записывать в телеметрию attempt: thermal state, давление памяти, swap до/после.
- Если воркер вернулся после сна — он делает `resume`; Orchestrator не считает это ошибкой рендера.
- Рендеры серией: пауза или ограничение на число подряд идущих тяжёлых job при признаках троттлинга.
- Фоновая работа пользователя на этом же Mac конкурирует за unified memory; в режиме рендера держать открытыми минимум приложений.

## 7. Генерация и контроль качества

### 7.1. Обязательный PoC видеомодели

**[ПРОВЕРИТЬ]** Исходник не доказывает, что предложенный стек `Wan 2.1 I2V + IP-Adapter WAN + ControlNet` существует в совместимой конфигурации и укладывается в 18 GB. Отдельно проверить:

1. Точный checkpoint, архитектуру, лицензию и доступный режим I2V.
2. Поддержку Apple MPS и используемых custom nodes.
3. Работу без IP-Adapter, затем с одним механизмом консистентности.
4. Потребление памяти и swap при 3–5 коротких генерациях подряд.
5. Скорость, разрешение, FPS, длительность, стабильность результата.

**Go/no-go:** получить воспроизводимый MP4 из стартового кадра и промпта без аварий, зафиксировать конфигурацию и ограничения. При провале выбрать более лёгкий workflow или внешний рендер как явный fallback.

#### Кандидаты для PoC [v1.2]

> Список основан на знаниях на середину 2026 года и **не проверен по актуальным репозиториям**. Перед PoC — часовой обзор свежих релизов и их поддержки в ComfyUI на Apple Silicon **[ПРОВЕРИТЬ]**.

| Кандидат              | Режим                       | Почему рассматривать                                                               | Что проверить                                                                                              |
| --------------------- | --------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Wan 2.2 TI2V-5B       | текст + изображение → видео | Наиболее правдоподобный по размеру для 18 GB (около 5B параметров, компактный VAE) | Работа на MPS, пик памяти текстового энкодера и VAE-декодера, квантование (GGUF и др.), нативный fps       |
| LTX-Video (семейство) | текст/изображение → видео   | Ориентировано на скорость и меньший расход памяти                                  | Качество движения и лиц, совместимость нод, лицензия                                                       |

**Профили генерации.** Завести два профиля с разными параметрами (низкое разрешение/мало кадров/мало шагов — `draft`; рабочее — `final`) и хранить профиль в attempt. Конкретные значения подобрать в PoC; сначала смотреть движение и композицию на `draft`, затем перегенерировать утверждённый шот на `final` с тем же seed.

### 7.2. Character consistency

Character bible — версионированный структурированный документ с постоянными атрибутами. Референсы — отдельные assets; timing — данные сцены. RAG предоставляет контекст, но не является источником истины для цвета одежды, особенностей внешности и иных обязательных атрибутов. Валидация LLM — вспомогательная; визуальная приёмка человеком обязательна. **[v1.2]** Дополнительно использовать объективный сигнал: сходство face-embedding кадров результата с эталонными референсами (ArcFace-подобные модели), записывать значение в attempt и показывать в review UI. Это сигнал для ревьюера, а не автоматический «одобрено/отклонено». Для непрерывности между шотами хранить `continuity_from_shot_id` и разделять keyframe-prompt (кто и где) и motion-prompt (что происходит): chaining по последнему кадру накапливает дрейф, поэтому периодически возвращаться к эталонному референсу.

### 7.3. Аудио и монтаж

TTS возвращает WAV, transcript, line/word timing с явной оценкой точности. Реплика может пересекать несколько шотов; шот может содержать несколько реплик. Монтажный этап должен задавать таймлайн, fps, audio mixing, переходы, экспорт и проверку A/V sync. **Это отсутствует в исходной реализации и включено в post-MVP.** **[v1.2]** Рекомендуемый формат таймлайна — OpenTimelineIO (или собственный JSON-EDL с версиями), сборка — ffmpeg. Постобработка (интерполяция кадров, апскейл, нормализация fps/кодека) — отдельные job kinds между рендером и монтажом: нативный fps модели обычно не совпадает с fps проекта.

### 7.4. Воспроизводимость

Для каждой попытки сохранять: версию prompt, seed, model checkpoint/hash, workflow JSON/hash, custom-node versions, параметры генерации, входные asset hashes, дату, устройство, duration, peak memory и итоговый файл. Даже с seed полная побитовая идентичность на разных версиях окружения не гарантируется.

### 7.5. Автоматические проверки результата [v1.2]

Перед переводом шота в `review` воркер/Orchestrator выполняет дешёвые проверки и сохраняет результат в attempt:

- `ffprobe`: валидный контейнер, ожидаемые число кадров, fps, разрешение, длительность;
- нет чёрных и полностью замороженных кадров; минимальный уровень движения;
- sha256 соответствует загруженному файлу;
- face-embedding similarity к эталону (если у шота есть персонаж).

Провал проверок не удаляет файл, а помечает attempt `qc_failed` с причиной.

### 7.6. Лицензии и происхождение моделей [v1.2]

Для каждого компонента (checkpoint, text encoder, VAE, LoRA, TTS-веса, custom node) вести реестр: источник, версия/hash, лицензия, ограничения (в том числе non-commercial и gated-доступ), допускает ли результат публикацию. Условия лицензий на веса часто отличаются от лицензии кода **[ПРОВЕРИТЬ для каждого компонента, включая TTS-модель в `VOICE_SYNTEZ`]**. Клонирование голоса реального человека — только с согласия; хранить факт согласия рядом с референсом.

## 8. Инфраструктура и безопасность

### 8.1. Размещение

|Linux controller|Mac factory|
|---|---|
|FastAPI, PostgreSQL, React static bundle, reverse proxy|Worker Agent, ComfyUI, Ollama, VOICE_SYNTEZ|
|Storage metadata и backup|Тяжёлые модели, временные рабочие файлы|

### 8.2. Безопасная конфигурация

- Не использовать `no_root_squash` как настройку по умолчанию; NFS экспортировать только доверенному IP/подсети с минимальными правами.
- Не публиковать PostgreSQL/Redis/ComfyUI/Ollama в интернет; ограничить firewall и доступ к LAN, при необходимости VPN.
- Worker API защищать токеном или mTLS; проверять авторизацию даже в домашней сети.
- Запретить произвольные абсолютные пути от клиента: разрешать только проверенные storage keys внутри workspace.
- Пароли — через `.env`/secrets, не коммитить; предусмотреть ротацию.
- Не принимать произвольные workflow JSON от внешних пользователей без ограничений: custom nodes могут выполнять код.
- Запускать сервисы от отдельных непривилегированных пользователей.
- **[v1.2]** ComfyUI и Ollama на Mac слушают только `127.0.0.1`; доступ извне — исключительно через Worker Agent.
- **[v1.2]** Orchestrator доступен Mac по TLS через reverse proxy на LAN-интерфейсе либо через VPN (например WireGuard); токен воркера хранится в `.env`/Keychain, поддерживается ротация.
- **[v1.2]** Custom nodes ComfyUI — исполняемый код из интернета: фиксировать commit, просматривать изменения перед обновлением, не обновлять автоматически.

### 8.3. Эксплуатация

- Health/readiness checks, structured logs, job_id/shot_id correlation.
- Метрики: очередь, время выполнения, failures/retries, RAM/swap, размер storage.
- Резервные копии PostgreSQL **и** файлов; периодический тест восстановления.
- Явная политика хранения черновиков и очистки временных файлов.
- `launchd` на macOS и systemd/Docker restart policy на Linux предпочтительнее набора `nohup`.

### 13.3. Claim-запрос и идемпотентность (PostgreSQL) [v1.2]

Шаблон; перед использованием проверить на своей схеме и добавить обработку `lease_expired`.

```sql
-- Не более одного активного render-job на шот (естественная идемпотентность)
CREATE UNIQUE INDEX one_active_render_per_shot
  ON jobs (shot_id)
  WHERE kind = 'render_video'
    AND status IN ('pending','leased','running','retry_wait','cancel_requested','lease_expired');

-- Захват задания воркером
WITH next AS (
  SELECT j.id
  FROM jobs j
  WHERE j.status IN ('pending','retry_wait')
    AND (j.run_after IS NULL OR j.run_after <= now())
    AND j.kind = ANY(:kinds)
    AND NOT EXISTS (
      SELECT 1 FROM job_dependencies d
      JOIN jobs p ON p.id = d.depends_on_job_id
      WHERE d.job_id = j.id AND p.status <> 'completed')
  ORDER BY j.priority DESC, j.created_at
  FOR UPDATE OF j SKIP LOCKED
  LIMIT 1)
UPDATE jobs
SET status = 'leased', lease_owner = :worker_id,
    lease_until = now() + interval '60 seconds',
    attempts = attempts + 1, updated_at = now()
FROM next
WHERE jobs.id = next.id
RETURNING jobs.*;
```

- Добавлены кандидаты для PoC и профили `draft`/`final`, автоматические проверки результата, реестр лицензий, формат таймлайна.
- Добавлены разбор спорных решений (2.3), две параллельные дорожки (A/B) с `FakeWorker`, таблица «обязательно / отложить», новые acceptance tests и риски.
- Добавлены claim-запрос, частичный уникальный индекс и пример конфигурации воркера.

## 14. Roadmap и инструкции ИИ-агентам [v1.3]

Этот раздел — рабочий план для ИИ-агентов, которыми управляет человек. Принцип: **один пакет работ (WP) за раз, после каждого — остановка и проверка человеком.** Агент не переходит к следующему WP без явного «продолжай».

### 14.1. Общие правила для любого агента (обязательны)

1. **Источник истины — этот документ.** Прочитать целиком до начала. Если задача противоречит документу или документ неоднозначен — остановиться и задать вопрос, не выбирать молча.
2. **Один WP за раз.** Работать в ветке `wp-<id>-<кратко>`, небольшими коммитами. Не мержить и не пушить в основную ветку самостоятельно.
3. **Не выдумывать факты.** Всё, что помечено **[ПРОВЕРИТЬ]**, проверяется по коду, документации или эксперименту; в отчёте указать источник (URL, commit/версия, дата) или команду, которой это проверено. Если проверить нельзя (нет доступа к Mac, нет сети) — прямо сказать и дать человеку команду для запуска.
4. **Не заявлять «готово» без запущенных проверок.** К отчёту прикладывать фактический вывод тестов/команд. Не ослаблять и не удалять тесты, чтобы они прошли.
5. **Опасные действия — только с явного разрешения человека:** `rm -rf`, удаление/сброс БД и миграций, `git push --force`, `sudo`, изменение файлов вне репозитория, установка системных пакетов, скачивание моделей и файлов больше 1 GB, открытие сетевых портов наружу.
6. **Секреты.** Не читать, не печатать и не коммитить `.env`, токены, ключи. В репозитории только `.env.example`.
7. **Чужие проекты в монорепо (`Mary_Guiness`, `VOICE_SYNTEZ`, `AI-IT-DEP` и др.) — только чтение.** Интеграция только через адаптеры по контрактам из §5; код из них не копировать и не править.
8. **Не расширять scope.** Раздел «Не делать» в каждом WP обязателен. Идея сверх плана — в `docs/IDEAS.md`, не в код.
9. **Зависимости.** Минимум, версии пинить (lockfile), перед добавлением проверить лицензию и поддержку. Custom nodes ComfyUI — только с зафиксированным commit.
10. **Сеть по умолчанию закрыта:** сервисы слушают `127.0.0.1`; ComfyUI и Ollama никогда не публикуются в LAN.
11. **Контракты неизменяемы без согласования:** схема БД (§4), API (§5), worker-протокол (§5.2–5.3). Нужна правка — оформить предложение в `docs/PROPOSALS/` и ждать решения.
12. **Формат отчёта** по завершении WP (см. 14.2).

### 14.2. Формат отчёта агента

```text
WP: <id и название>
Статус: готово / частично / заблокировано
Что сделано: <кратко, список файлов>
Как проверено: <команды и фактический вывод тестов>
Отклонения от документа: <нет / список с причиной>
Не удалось проверить [ПРОВЕРИТЬ]: <что и какой командой проверить человеку>
Открытые вопросы к человеку: <список>
Предложение следующего шага: <WP-id>
```

### 14.3. Порядок работ и зависимости

```text
WP-00 (подготовка)
   |
   +--> Дорожка A [Mac-агент]:      A1 -> A2 -> A3 -> A4 -> (A5)  ==> Gate A
   |
   +--> Дорожка B [Linux-агент]:    B1 -> B2 -> B3 -> B4 -> B5 -> B6 -> B7 -> B8  ==> Gate B
                                                  
Gate A + Gate B --> I1 -> I2 -> I3  ==> Gate I (вертикальный срез на железе)
Gate I --> U1 -> U2  ==> MVP
MVP --> P1 ... P7 (после MVP, по одному)
```

Дорожки A и B независимы и могут вестись **двумя агентами параллельно**: Linux-агент работает с Orchestrator на `FakeWorker`, Mac-агент — с ComfyUI на реальном железе. Каждый агент работает в своей ветке и не трогает файлы другой дорожки.

### 14.4. WP-00. Подготовка

**Агент:** любой. **Зависит от:** ничего.

- Создать структуру репозитория: `orchestrator/`, `worker/`, `ui/`, `workflows/`, `tests/`, `docs/` (`docs/poc/`, `docs/PROPOSALS/`), положить этот документ в `docs/ARCHITECTURE.md`.
- Создать `docs/DECISIONS.md` со списком открытых решений из §12 (№5–9, 11–13, 15) — **только вопросы и варианты, без выбора**.
- Создать `docs/ENV-AUDIT.md`: версии ОС, RAM, Python, Node, ffmpeg, Docker на Linux и на Mac (скрипт `scripts/env_audit.sh`, который выводит только версии, без секретов и путей к личным данным).
- Скопировать правила 14.1 в `AGENTS.md` в корне репозитория.

**Не делать:** писать код сервисов, скачивать модели, выбирать технологии за человека. **Готово когда:** структура создана, `DECISIONS.md` и `ENV-AUDIT.md` заполнены. **Чекпоинт человека:** отвечает на вопросы в `DECISIONS.md` (особенно №7 «превизуализация или финал», №11 источник кадров, №13 облако).

### 14.5. Дорожка A — feasibility модели (Mac-агент)

**WP-A1. Обзор моделей и лицензий.** Зависит от: WP-00.

- Составить `docs/poc/MODEL-SURVEY.md` по кандидатам из §7.1 и по более новым релизам, если они есть: режим (I2V/TI2V), размер, формат весов (в том числе квантованные), поддержка в ComfyUI и на Apple Silicon (MPS), необходимые custom nodes, **лицензия весов и кода**, ссылки на репозитории с commit и датой проверки.
- Предложить 2 кандидата для PoC: основной и запасной, с обоснованием.
- Не скачивать модели. **Готово когда:** для каждого кандидата заполнены все поля, непроверенное помечено **[ПРОВЕРИТЬ]**. **Чекпоинт:** человек выбирает кандидата(ов) и разрешает загрузку.

**WP-A2. Установка ComfyUI на Mac.** Зависит от: A1.

- Установить ComfyUI в отдельном venv; зафиксировать commit ComfyUI и версии нод в `workflows/LOCK.md`, зависимости — в lockfile.
- Слушать только `127.0.0.1`. Запустить встроенный пример для любой лёгкой модели, чтобы проверить MPS.
- Скачивание весов выбранного кандидата — после разрешения человека (размер указать заранее). **Не делать:** ставить custom nodes без записи commit; обновлять ComfyUI после фиксации. **Готово когда:** тестовая генерация проходит, версии зафиксированы.

**WP-A3. Серия PoC-рендеров.** Зависит от: A2.

- Скрипт телеметрии `scripts/mac_telemetry.sh`: память (`vm_stat`, `memory_pressure`), swap (`sysctl vm.swapusage`), thermal (`pmset -g therm`), до/после/во время рендера.
- 3–5 коротких рендеров подряд в профиле `draft` (§7.1) из одного стартового кадра и промпта; затем один в профиле `final`. Сохранить workflow в API-формате (`workflows/<name>.api.json`), входы, выходы, seed, время, пик памяти.
- Проверить воспроизводимость: повтор с тем же seed и окружением, зафиксировать, насколько результат совпадает.
- Отчёт `docs/poc/POC-REPORT.md` с таблицей замеров и выводом **go / no-go** по критериям §7.1. **Не делать:** подключать IP-Adapter/ControlNet до успешного baseline; оптимизировать преждевременно. **Чекпоинт:** человек смотрит видео и цифры, принимает решение go/no-go и выбор модели.

**WP-A4. Эксперименты API ComfyUI.** Зависит от: A2 (может идти параллельно с A3).

- Документ `docs/poc/COMFY-API-NOTES.md`: фактическое поведение на зафиксированной версии: отправка prompt, `/history/{prompt_id}`, WebSocket-прогресс, `/interrupt`, удаление из очереди, `/free`, поведение после перезапуска ComfyUI (что известно о prompt_id), поведение при OOM. Каждое утверждение — с командой, которой проверено.
- Тесты: cancel во время sampling; cancel ожидающего prompt; `/free` и фактическое освобождение памяти; сон Mac во время рендера. **Готово когда:** закрыты пункты **[ПРОВЕРИТЬ]** из C13, C24 и §12 №14.

**WP-A5 (по решению человека). Консистентность персонажа.** Зависит от: A3 go.

- Сначала baseline без адаптеров; затем один механизм консистентности, совместимый с выбранной моделью; метрика — face-embedding similarity (§7.2, §7.5). Отчёт с результатами и ограничениями.

**Gate A:** есть воспроизводимый MP4 из стартового кадра и промпта, зафиксированы модель, workflow, версии, лимиты по кадрам/разрешению/памяти, проверены cancel/free. Без Gate A не начинается WP-I1.

### 14.6. Дорожка B — Orchestrator на FakeWorker (Linux-агент)

**WP-B1. Каркас Orchestrator.** Зависит от: WP-00.

- FastAPI + SQLAlchemy 2 + Alembic + PostgreSQL (docker compose по шаблону §13.1, но без `MAC_WORKER_URL`); конфигурация через переменные окружения, `GET /api/health`.
- Модели и миграции только для `projects`, `scenes`, `shots`; CRUD для них; pytest, линтер, форматтер; команда `make test` / эквивалент. **Не делать:** очередь, воркер, UI. **Готово когда:** `pytest` зелёный, миграции применяются и откатываются на чистой БД.

**WP-B2. Схема очереди и попыток.** Зависит от: B1.

- Таблицы `prompt_revisions`, `jobs`, `job_dependencies`, `render_attempts`, `artifacts`, `reference_assets`, `workers` по §4.1; `CHECK` «ровно один из scene_id/shot_id», enum/`CHECK` статусов, частичный уникальный индекс из §13.3, уникальность `(scene_id, sequence_no)`.
- Тесты на ограничения (нарушение должно приводить к ошибке БД). **Готово когда:** все ограничения покрыты тестами.

**WP-B3. Хранилище артефактов.** Зависит от: B2.

- Загрузка с заголовком `X-Content-SHA256`, сервер сам считает хэш, content-addressed хранение, атомарная публикация (временный файл → проверка → rename → запись Artifact), скачивание по `artifact_id`.
- Только относительные storage keys; тесты на path traversal, неверный хэш, оборванную загрузку, повторную загрузку. **Не делать:** NFS/SMB.

**WP-B4. Очередь и Worker API.** Зависит от: B3.

- Чистый модуль конечного автомата статусов Job/Shot (§4.2) с юнит-тестами на все переходы, включая недопустимые.
- Эндпоинты `claim` (claim-запрос из §13.3), `heartbeat`, `artifacts`, `complete`, `fail`, `resume` (§5.1); фоновая проверка истёкших lease → `lease_expired` (без автоматического перезапуска).
- Авторизация токеном воркера.
- Тест конкурентности: два claimer одновременно — job достаётся ровно одному; зависимости соблюдаются. **Готово когда:** тесты конкурентности и state machine зелёные. **Чекпоинт:** человек ревьюит SQL claim, конечный автомат и обработку `lease_expired` — это ядро надёжности.

**WP-B5. FakeWorker и сценарии сбоев.** Зависит от: B4.

- `FakeWorker` реализует worker-протокол: настраиваемые задержки, прогресс, сбои, обрыв связи, «сон», дубликаты; результат — маленький валидный MP4 (генерируется через ffmpeg).
- Автотесты по списку §6.3 и новым пунктам: рестарт Orchestrator при `running`, потеря воркера, гонка claim, обрыв загрузки, cancel, повторный `render`. **Готово когда:** сценарии §6.3 реализованы как автотесты и проходят.

**WP-B6. Публичный API и события.** Зависит от: B5.

- Эндпоинты из §5.1 (в том числе `render`, `cancel`, `approve`/`reject`, `keyframe`), `202 Accepted` на постановку job, единый формат ошибок, пагинация, валидация.
- SSE `/api/events` с `sequence`; источник истины — `GET /api/jobs/{id}`.
- OpenAPI-схема в репозиторий; контрактные тесты. **Готово когда:** сквозной тест «shot → render → FakeWorker → MP4 → attempt → approve» зелёный.

**WP-B7. Базовая безопасность.** Зависит от: B6.

- Аутентификация публичного API (токен), `127.0.0.1` по умолчанию, валидация storage keys, `.env.example`, проверка отсутствия секретов в репозитории, настройка reverse proxy с TLS для Mac (инструкция, без внешних портов).

**WP-B8. Референсы и стартовый кадр (ручная загрузка).** Зависит от: B6.

- Загрузка референса как `reference_assets`/артефакта, привязка к шоту как стартовый кадр, статус `keyframe_ready`; запрет постановки render без подтверждённого кадра. **Не делать:** T2I-генерацию.

**Gate B:** все автотесты дорожки B зелёные, сквозной сценарий проходит на FakeWorker, acceptance tests из §10, не требующие модели, выполнены.

### 14.7. Интеграция на железе

**WP-I1. Реальный Worker Agent (Mac-агент).** Зависит от: Gate A, Gate B.

- Pull-цикл: `claim` → скачивание входов с проверкой `sha256` → подготовка workflow из шаблона (именованные параметры, §5.2, D6) → запуск в ComfyUI → heartbeat и прогресс → загрузка результата → `complete`.
- Resource manager (§6.2): единый lock, проверка памяти, выгрузка по механизмам, подтверждённым в A4; сверка фактического состояния памяти.
- `resume` после рестарта; cancel по правилам C24; телеметрия в attempt (peak RAM, thermal, длительность).
- Запуск через `launchd` + `caffeinate -i` (§6.4), токен из `.env`/Keychain. **Не делать:** Ollama/TTS/Whisper в этом WP; параллельные задания. **Готово когда:** воркер проходит контрактные тесты из B5 в режиме «реальный ComfyUI, фиктивный Orchestrator».

**WP-I2. Вертикальный срез.** Зависит от: I1.

- Один реальный шот: референс → render → MP4 → просмотр → approve; повторный render создаёт новую версию, старая сохраняется.
- Прогнать acceptance tests §10 на реальном железе, результаты — в `docs/ACCEPTANCE-RESULTS.md`.

**WP-I3. Надёжность на железе.** Зависит от: I2.

- Реальные сценарии: сон Mac во время sampling, kill воркера и ComfyUI, обрыв сети, перезапуск Linux при `running`, cancel, две одинаковые команды `render`, OOM.
- Исправить найденные дефекты, добавить регрессионные тесты.

**Gate I:** все acceptance tests §10 пройдены на железе; нет ложных `completed` и дублей рендеров.

### 14.8. MVP: интерфейс и эксплуатация

**WP-U1. Минимальный интерфейс.** Зависит от: Gate I. Сначала CLI и OpenAPI `/docs`; затем простой UI: список шотов, карточка шота (промпт, версии попыток, видеоплеер, approve/reject), очередь с прогрессом через SSE. Стек — по решению человека. **Не делать:** Kanban, редакторы таймлайна.

**WP-U2. Резервные копии и очистка.** Зависит от: U1. Скрипт backup PostgreSQL и медиа, **тест восстановления на чистой машине** (результат — в документ), политика retention промежуточных файлов (§4.3).

**MVP считается готовым** после U2 и повторного прохождения всех acceptance tests.
