## 3. Новый движок (§2 задания)

`backend/app/viseme_blend.py`, `MODE = WORKFLOW_VERSION = ENGINE = "viseme_frame_blend_v1"`.

Вход:

- approved-источник: approved-референс шота либо утверждённый стартовый кадр;
- пять согласованных изображений морды `closed` / `small_open` / `medium_open` /
  `wide_open` / `rounded`;
- запись (утверждённый `shot_audio`) — исходная дорожка без пересэмплирования в результат;
- viseme timing JSON (`timing`, `timing_source='payload'`) либо Rhubarb
  (`use_rhubarb=true`, `timing_source='rhubarb'`);
- конфигурация blending: `blend_ms`, `min_hold_ms`.

Как собирается кадр:

1. Патч области морды (калибровка + запас 4 %) берётся **из реального изображения
   набора**, остальные пиксели — из approved-источника без изменений. Маска рта не
   рисуется.
2. На каждом кадре используется не более двух изображений: `primary` + `secondary`
   с весом `mix` (`Image.blend`), поэтому границы виземов — кросс-фейд, а не склейка.
3. Вес сглаживается с постоянной времени `blend_ms` (по умолчанию 60 мс) — скорость
   изменения артикуляции ограничена, дрожания нет.
4. Виземы короче `min_hold_ms` (60 мс) отбрасываются.
5. В промежутках между виземами (паузах) рот закрывается (`closed`).
6. FFmpeg: `rawvideo/rgb24` pipe → `libx264 -preset veryfast -crf 20 -pix_fmt yuv420p`
   + `aac -b:a 192k -af apad -t <frames/fps>`, `+faststart`; результат обязан пройти
   `probe_mp4` с непустой аудиодорожкой. Звук — исходная запись, без ре-энкода в WAV-цепочке.

Выход: MP4 (h264 + AAC), `Artifact(kind='talking_preview', mime='video/mp4')`,
`RenderAttempt(kind='video', workflow_version='viseme_frame_blend_v1')` с параметрами
(`engine`, `timing_source`, `timings`, `viseme_set`, `compatibility`, `blend_ms`,
`min_hold_ms`), `Job(kind='mouth_animation')`. Review — существующими эндпоинтами.

Ограничение движка зафиксировано в `LIMITATION`: артикуляция ограничена пятью формами
рта, это не генеративный pixel-level lip sync.

## 5. API и проверка совместимости (§3–§4 задания)

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/shots/{shot_id}/viseme-set` | состав набора, `missing`, `ready`, `blockers`, `metrics`, `preview_url` |
| `GET` | `/api/shots/{shot_id}/viseme-set/preview` | PNG-лист сравнения: источник + пять вариантов с рамкой области морды |
| `POST` | `/api/shots/{shot_id}/viseme-set/{state}` | импорт кадра (сырое тело, PNG/JPEG, ≤ 32 МиБ), статус `draft` |

Проверка (`backend/app/viseme_assets.py`, PIL + `ImageChops`, без numpy):

| Проверка | Метрика | Порог / блокер |
|---|---|---|
| Разрешение всех кадров совпадает с источником | размеры | `viseme_resolution_mismatch` |
| Сдвиг головы | поиск по сетке ±8 px вне области морды, порог улучшения 0.5 | `viseme_head_shift` |
| Изменения вне области морды | доля изменённых пикселей (`delta > 12`) | ≤ 1 % (`viseme_outside_mouth_changes`) |
| `closed` совпадает с источником | доля изменений внутри области морды | ≤ 1 % (`viseme_closed_mismatch`) |
| Есть заметная артикуляция | доля изменений внутри области | ≥ 0.5 % (`viseme_no_articulation`) |
| Риск мерцания между вариантами | максимум попарных различий вне морды | ≤ 1 % (`viseme_flicker_risk`) |
| Полнота и утверждение | наличие всех пяти состояний | `viseme_set_incomplete`, `viseme_set_not_approved` |

Если набор не прошёл — `POST …/mouth-animation` с `engine='viseme_frame_blend_v1'`
отдаёт 409 `viseme_set_blocked` с `missing` и `blockers` **до** создания Job/RenderAttempt.

## 8. Требования к viseme-ассетам (что именно нужно)

Нужны **пять изображений одной и той же морды Гиннесса**, снятых в одном кадре,
ракурсе, освещении и с одним фоном. Меняется только форма рта.

| Состояние | Форма рта |
|---|---|
| `closed` | губы сомкнуты, челюсть в покое (может быть неявно взят из approved-источника) |
| `small_open` | челюсть чуть опущена, видна узкая полоска пасти |
| `medium_open` | челюсть опущена заметно, рот открыт, язык не активен |
| `wide_open` | максимальное раскрытие челюсти (гласные А/Э) |
| `rounded` | губы вытянуты вперёд, округлое отверстие (О/У) |

Технические требования (проверяются автоматически, при нарушении генерация блокируется):

1. **Разрешение 941×1672** (как approved-источник `d2767fbd…`), PNG или JPEG, RGB/RGBA,
   ≤ 32 МиБ. Другой размер → `viseme_resolution_mismatch`.
2. **Никакого масштабирования, кропа и повторного сэмплирования** между вариантами:
   пиксели вне морды должны совпадать с источником.
3. **Изменения вне области морды ≤ 1 %** пикселей (порог чувствительности 12/255):
   глаза, нос, усы, шерсть, уши, фон, свет — без изменений
   (`viseme_outside_mouth_changes`).
4. **Сдвиг головы ≤ 8 px** (≈0.85 % ширины): кадр не смещён и не повёрнут
   (`viseme_head_shift`).
5. **`closed` совпадает с approved-источником ≤ 1 %** внутри области морды
   (`viseme_closed_mismatch`).
6. **Артикуляция заметна: ≥ 0.5 %** пикселей внутри области морды изменены в каждом
   открытом варианте (`viseme_no_articulation`).
7. **Нет мерцания: попарные различия вне морды ≤ 1 %** — иначе набор «дёргается»
   (`viseme_flicker_risk`).
8. Все пять кадров утверждены человеком; загрузка создаёт только `draft`.

Что **нельзя** делать: генерировать варианты автоматически без согласования,
перезаписывать approved-источник, подмешивать другой ракурс/свет/фон, «дорисовывать»
глаза и усы заново, отдавать изображения с другим кадрированием.

## 9. Способ подготовки (рекомендация)

1. Взять approved-кадр `d2767fbd…` (941×1672) как базу и как эталон `closed`.
2. Подготовить четыре открытых варианта **слоями** в графическом редакторе на копии
   базы: нижняя челюсть/подбородок и внутренняя часть пасти двигаются, глаза, нос,
   усы, уши, фон и освещение остаются пиксельно нетронутыми. Без генеративного
   заполнения и без AI-инпейнтинга, который меняет область вне морды.
3. Экспортировать все четыре файла в том же размере 941×1672 (PNG, без
   пересэмплирования).
4. Загрузить каждый файл в панели «4. Viseme-кадры» (`POST …/viseme-set/{state}`),
   открыть лист сравнения и убедиться, что различия только в области морды.
5. Утвердить кадры человеком (`approve` существующим эндпоинтом).
6. Только после `ready: true` запускать сборку.

Если подготовка невозможна без генерации новых изображений — нужен отдельный
разрешённый шаг: какие именно кадры генерировать и каким инструментом.

## 10. Rhubarb 1.14.0 (§5 задания)

- Адаптер `backend/app/rhubarb.py`: `VERSION = "1.14.0"`, лицензия MIT, проверка
  наличия, бита исполнения, каталога `res/`, архитектуры через `file -b` и SHA-256 из
  `MARY_RHUBARB_SHA256`.
- **Официальная сборка macOS — только `x86_64`** (в релизе v1.14.0 три ассета: Linux,
  macOS, Windows; arm64-сборки нет). Проверка расширена по решению человека: `arm64`
  принимается как есть, `x86_64` — только при доступной Rosetta 2 (`arch -x86_64
  /usr/bin/true`), с пометкой `rosetta: true` и записью `notes[0].code =
  "rhubarb_runs_under_rosetta"`. SHA-256 остаётся обязательным и строгим.
- Бинарник установлен вручную человеком с разрешения: `~/.mary-studio/tools/rhubarb-1.14.0/`
  (`rhubarb` 8 425 288 Б, `res/`, `LICENSE.md`). Архив релиза —
  `Rhubarb-Lip-Sync-1.14.0-macOS.zip`, 86 870 942 Б, sha256 архива
  `f991deacac6c973a14a4431a16a58b842f436531e120cfaea142c87c0d3ab4c5`; **SHA-256
  запинен по бинарнику** (не по архиву): `93fa4a16ae1cc88a89d59743057521407843fc7139e23808c9e6587c6cc946d3`
  (`MARY_RHUBARB_SHA256`, не в коде). `./rhubarb --version` → `Rhubarb Lip Sync
  version 1.14.0`, `LICENSE.md` — MIT. Скачиваний из приложения нет
  (`download_performed: false`).
- `GET /api/rhubarb/status` → `installed:true`, `verified:true`, `reasons: []`,
  `arch: "Mach-O 64-bit executable x86_64"`, `rosetta: true`.
- **Ограничение входа:** Rhubarb принимает только `.wav` и `.ogg`; MP3 отклоняется с
  понятной ошибкой `rhubarb_input_unsupported` (проверено живьём: `.mp3` → отказ
  бинарника «Unsupported file extension»). Рабочая PCM-копия записи `shot_audio` —
  WAV 48 кГц, поэтому штатный путь работает без конвертации.
- `analyze()` больше не пишет временный JSON рядом с записью: вывод идёт во временный
  каталог. Живой прогон на записи `Lana 6-4.mp3` (WAV-копия, 11.86 с) — **82 виземных
  интервала**: `small_open` 26, `closed` 24, `medium_open` 22, `rounded` 10,
  `wide_open` 0 (форма D на этой записи не встретилась), последний интервал
  `11.26–11.83` — `closed`.
- `parse_output` читает JSON (`mouthCues`, формы A–F, G, H, X) и отображает в пять
  состояний; `check_pauses` отмечает паузы без закрытого рта.
- До установки `use_rhubarb=true` давал явную 409, а не тихий fallback; это поведение
  сохранено для случая, когда бинарник не проверен.

## 14. Отклонения от плана

1. **Поиск сдвига головы.** На однородном фоне все сдвиги давали одинаковый ноль и
   «выигрывал» крайний сдвиг `(-limit, -limit)`. Введена базовая гипотеза `(0,0)` и
   порог улучшения `SHIFT_MIN_GAIN = 0.5`: сдвиг признаётся только при реальном
   уменьшении различий. Без этого ложные `viseme_head_shift` блокировали бы корректные
   наборы.
2. **Источник по умолчанию.** Если у шота нет стартового кадра, но есть approved-референс,
   отчёт и импорт берут его (`_default_source_reference`, приоритет роли `*_start`),
   иначе любой такой шот был бы заблокирован `source_image_required`.
3. **Провенанс в тестах** читается из `render_attempts.parameters` напрямую: API отдаёт
   только подмножество `RENDER_PARAMETER_KEYS`, и `engine`/`timings` в ответ не попадают.
4. **Порог листа сравнения в тесте** ослаблен до `width > 2·height` — шесть плиток дают
   соотношение около 4:1, прежнее утверждение было арифметически неверным.
5. **Архитектура Rhubarb.** Адаптер требовал `arm64`, а официальная сборка macOS
   v1.14.0 — `x86_64` (arm64-релиза у проекта нет). По решению человека проверка
   расширена: `x86_64` принимается только при доступной Rosetta 2, с пометкой в статусе
   (`rosetta: true`, `notes`), SHA-256 остаётся строгим. Оговорка внесена в
   `docs/DECISIONS.md` §4.21 п.6.
6. **Каталог `res/`.** `DEFAULT_BINARY` указывает на один файл, но Rhubarb ищет модели
   рядом с собой; добавлена проверка `res_missing` (блокер), чтобы не ловить невнятную
   ошибку в рантайме.
7. **Вход Rhubarb.** Бинарник не читает MP3 (только `.wav`/`.ogg`); добавлен явный
   `rhubarb_input_unsupported`. Штатный путь (`shot_audio` → PCM WAV) не затронут.
